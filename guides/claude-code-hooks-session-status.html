Using Claude Code hooks to track session status

Updated August 26, 2026

Claude Code's hooks run your own shell commands at well-defined points in a session's lifecycle — when Claude starts a tool call, finishes a turn, or stops to wait for your input. That makes them the building blocks for anything from a simple "ping me when it's waiting" to a full session-status dashboard. This guide explains the model and walks through working examples.

How hooks work

Hooks are configured under the "hooks" key of your settings — typically ~/.claude/settings.json for all projects, or .claude/settings.json inside a repo. Each entry maps a lifecycle event to one or more commands: 

{
  "hooks": {
    "Notification": [
      {
        "hooks": [
          { "type": "command", "command": "your-command-here" }
        ]
      }
    ]
  }
}

When the event fires, Claude Code runs the command and pipes a JSON payload to its stdin. The payload always identifies the session — session_id, cwd, transcript_path, hook_event_name — plus event-specific fields such as tool_name and tool_input for tool events, or a human-readable message for Notification. Tool events also support a matcher to filter by tool name.

The events that matter for session status

Claude Code exposes many hook events; for tracking what a session is doing, these are the core ones:

EventFires when…
SessionStarta session starts or resumes — the row "appears".
UserPromptSubmityou submit a prompt — the session goes "running".
PreToolUse / PostToolUsearound each tool call — the fine-grained "what is it doing" signal.
NotificationClaude is waiting — for a permission decision or for your input.
StopClaude finishes responding — the task is done.
SubagentStopa subagent finishes its work.
SessionEndthe session ends — the row "disappears".

Example 1: macOS notification when a session is waiting

The classic quality-of-life hook. In ~/.claude/settings.json: 

{
  "hooks": {
    "Notification": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Waiting for your input\" with title \"Claude Code\" sound name \"Glass\"'"
          }
        ]
      }
    ]
  }
}

More macOS-specific variants (terminal bell, iTerm2/Ghostty native notifications, sounds on Stop) are covered in Claude Code notifications on macOS.

Example 2: write each session's state to a status file

Notifications are transient; a status file can be read any time — by your shell prompt, a tmux status bar, or a script. This setup keeps one JSON file per session under ~/.claude/session-status/, updated as sessions change state: 

{
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh running" } ] }
    ],
    "Notification": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh waiting" } ] }
    ],
    "Stop": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh done" } ] }
    ],
    "SessionEnd": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh ended" } ] }
    ]
  }
}

And ~/.claude/track-status.sh (make it executable with chmod +x):

#!/bin/bash
# Reads the hook payload on stdin, writes one status file per session.
STATE="$1"
DIR="$HOME/.claude/session-status"
mkdir -p "$DIR"

PAYLOAD=$(cat)
SESSION_ID=$(echo "$PAYLOAD" | jq -r '.session_id')
CWD=$(echo "$PAYLOAD" | jq -r '.cwd')

if [ "$STATE" = "ended" ]; then
  rm -f "$DIR/$SESSION_ID.json"
else
  jq -n --arg state "$STATE" --arg cwd "$CWD" \
    '{state: $state, cwd: $cwd, updated: now | todate}' \
    > "$DIR/$SESSION_ID.json"
fi

Now cat ~/.claude/session-status/*.json shows the live state of every session, and anything that can read a file — a tmux segment, a menu-bar script — can render it.

What it takes to turn hooks into a real monitor

The status-file approach genuinely works, and it's a great way to understand the lifecycle. But going from "files on disk" to "something I can trust at a glance" involves a long tail of work:

  • Distinguishing why a session is waiting — a permission prompt, a question, and a plan review all deserve different urgency; the payload gives you raw material, not a classification.
  • Cleaning up stale state — sessions killed with Ctrl-C or a closed terminal may never fire SessionEnd, so files go stale.
  • A UI you'll actually look at — polling files from tmux is fine until the one day you're not in tmux; a monitor only helps if it's always in view when it matters.
  • Jumping back — knowing session abc123 is waiting still leaves you hunting for the right terminal tab or IDE window.
