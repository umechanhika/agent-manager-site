Claude Code notifications on macOS: never miss a prompt

Updated August 26, 2026

Claude Code often works autonomously for minutes — then stops and quietly waits: for permission to run a command, for an answer to a question, or simply because it's done. If you've switched to Slack or your browser in the meantime, nothing tells you. Here is every practical way to get notified on macOS, from a one-line setting to custom hooks.

Why you keep missing prompts

By default, a waiting Claude Code session is completely silent. The prompt sits in a terminal tab that isn't focused, doesn't bounce the Dock, and doesn't ring. The longer Claude's autonomous stretches get, the more likely you are to be somewhere else when it stops. The result is a familiar loop: you check the terminal "just in case", find Claude has been waiting for eight minutes, approve, switch away, repeat.

Option 1: native notifications from your terminal

The easiest path, if you use a supported terminal: Claude Code can post macOS desktop notifications through Ghostty, Kitty, and iTerm2 when it's waiting for you.

  • Ghostty / Kitty — works out of the box; just allow notifications for the app when macOS asks.
  • iTerm2 — enable it first: Settings → Profiles → Terminal → check the notifications option ("Send Notification Center alerts"), and allow iTerm2 notifications in macOS System Settings.

Apple's stock Terminal.app has no such integration — for that, use the bell or hooks below.

Option 2: the terminal bell

Claude Code can ring the terminal bell when it needs attention. Set it in ~/.claude/settings.json: 

{
  "preferredNotifChannel": "terminal_bell"
}

Most terminals turn the bell into something visible: Terminal.app shows a badge on the tab, iTerm2 can post a notification for it, and tmux marks the window with a bell indicator. It's crude, but it works everywhere and needs no scripts.

Option 3: hooks — full control over notifications

For anything custom, Claude Code's hooks run a shell command of your choice at lifecycle events. Two events matter for notifications:

  • Notification — fires when Claude is waiting for permission or for your input.
  • Stop — fires when Claude finishes responding, i.e. the task is done.

This ~/.claude/settings.json posts a macOS notification whenever any session needs you, and plays a sound when a task completes: 

{
  "hooks": {
    "Notification": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude Code is waiting for your input\" with title \"Claude Code\" sound name \"Glass\"'"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "afplay /System/Library/Sounds/Ping.aiff"
          }
        ]
      }
    ]
  }
}

Hook commands also receive a JSON payload on stdin — including session_id, cwd, and for the Notification event a message field — so a small script can include which project is asking in the notification text. See the companion guide on tracking session status with hooks for worked examples.

Gotchas: macOS Focus modes silence display notification banners like any other notification, and the first osascript notification may trigger a permission prompt for your terminal app. Test your hook with a short dummy task before relying on it.

The limits of fire-and-forget notifications

All three options share one shape: a one-shot ping at the moment something happens. That's enough for a single session — and noticeably not enough once you run several sessions in parallel:

  • A banner vanishes after a few seconds; a bell is gone the moment it rings. Miss it once and you're back to polling tabs.
  • Notifications don't show current state — which sessions are still waiting right now, which already got handled.
  • They rarely tell you what kind of attention is needed: a one-keystroke permission, a design question, or a finished task you should review.
