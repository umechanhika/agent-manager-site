How to manage multiple Claude Code sessions

Updated August 26, 2026

Claude Code can work on a task for minutes at a time — which makes it natural to open a second session, then a third, and keep them all busy in parallel. The hard part isn't starting the sessions. It's keeping track of them: which one is still running, which one finished, and which one has been silently waiting for your permission for the last ten minutes. This guide covers a practical setup for parallel Claude Code work.

Why run more than one session at all?

A single Claude Code session is often your bottleneck in reverse: Claude works, you wait. Typical reasons to parallelize:

  • Independent tasks — a bug fix in one repo, a refactor in another, a doc update in a third.
  • Long-running work — while one session runs a migration or a large test suite, another can review a PR.
  • Exploration vs. execution — one session investigates a design question while another implements something already decided.

The trade-off: every extra session multiplies the chances that one of them is blocked on you without you noticing. Claude Code stops and waits whenever it needs a permission decision (running a command, editing a file), an answer to a question, or approval of a plan. A waiting session makes no sound and steals no focus — it just sits there.

1. Give each session its own working copy (git worktrees)

Running two sessions in the same checkout is asking for trouble: both edit the same files, and one session's git status becomes noise for the other. If your parallel tasks touch the same repository, give each session its own git worktree: 

cd ~/code/myapp
git worktree add ../myapp-fix-login fix/login-timeout
git worktree add ../myapp-refactor refactor/db-layer

# terminal tab 1
cd ../myapp-fix-login && claude

# terminal tab 2
cd ../myapp-refactor && claude

Each worktree is a full checkout on its own branch sharing one .git store, so it's cheap, and sessions can never step on each other's uncommitted changes. When a task is done, git worktree remove cleans up.

2. Make sessions identifiable in your terminal

With three or more sessions, "which tab was the API refactor?" becomes a real question. A few habits help:

  • One tab (or tmux window) per session, named after the task — most terminals let you rename tabs; in tmux it's tmux rename-window api-refactor.
  • A consistent order — e.g. leftmost tab is always the "main" task.
  • A status line inside Claude Code — the /statusline command sets up a custom status line (model, git branch, context usage) so each session is self-describing. It can also be configured manually via the statusLine setting in ~/.claude/settings.json.

3. Get notified when a session needs you

Naming tabs solves "which one is which", but not "which one needs me right now". Claude Code has several built-in ways to surface that moment:

  • Native terminal notifications — in Ghostty, Kitty, and iTerm2, Claude Code can post desktop notifications when it's waiting (iTerm2 requires enabling notifications in Settings → Profiles → Terminal).
  • Terminal bell — set "preferredNotifChannel": "terminal_bell" in ~/.claude/settings.json, and most terminals will mark the tab that rang.
  • Hooks — the Notification hook event fires when Claude is waiting for input or permission, and can run any command, such as posting a macOS notification.

We cover both approaches in detail in the companion guides: Claude Code notifications on macOS and tracking session status with hooks.

Where this setup breaks down

Notifications tell you that something happened, once. With several sessions running, that's not quite the same as knowing the state of your fleet:

  • A macOS banner disappears after a few seconds. If you were mid-thought in another session, it's gone.
  • Two notifications in a row don't tell you which sessions are still waiting versus already handled.
  • You can't tell what kind of attention is needed — a quick yes/no permission, a plan to review, or a finished task — without switching to the tab and looking.
  • The mental overhead grows with every session: you end up polling your own terminal tabs like a human cron job.

What actually scales is a persistent, glanceable view of every session's status — the thing an IDE gives you for build tasks, but for your Claude Code sessions.
