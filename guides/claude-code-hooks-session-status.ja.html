Claude Code の hooks でセッション状態を把握する

更新日: 2026年8月26日

Claude Code の hooks は、セッションのライフサイクル上の決まったタイミング — ツール実行の前後、 応答の完了、入力待ちへの移行など — で自作のシェルコマンドを実行できる仕組みです。 「待ちになったら知らせる」という小さな用途から、セッション状態ダッシュボードの構築まで、 すべての土台になります。この記事では hooks のモデルを説明し、動く設定例を順に組み立てます。

hooks の仕組み

hooks は設定ファイルの "hooks" キーで構成します。全プロジェクト共通なら ~/.claude/settings.json、リポジトリ単位ならリポジトリ内の .claude/settings.json です。各エントリはライフサイクルイベントに 1 つ以上のコマンドを対応付けます。 

{
  "hooks": {
    "Notification": [
      {
        "hooks": [
          { "type": "command", "command": "実行したいコマンド" }
        ]
      }
    ]
  }
}

イベントが発火すると、Claude Code はコマンドを実行し、stdin に JSON ペイロードを渡します。 ペイロードには必ずセッションを特定する情報 — session_id・cwd・ transcript_path・hook_event_name — が含まれ、さらにイベント固有の フィールドが付きます。ツール系イベントなら tool_name と tool_input、 Notification なら人間向けの message です。ツール系イベントは matcher でツール名によるフィルタもできます。

セッション状態の把握に効くイベント

Claude Code には多数のフックイベントがありますが、セッションの状態追跡という目的では 次が中心になります。

イベント発火タイミング
SessionStartセッションの開始・再開 — 一覧に行が「現れる」瞬間。
UserPromptSubmitプロンプトの送信 — セッションが「実行中」になる。
PreToolUse / PostToolUse各ツール実行の前後 — 「今なにをしているか」の細粒度シグナル。
NotificationClaude が待ちに入った — 許可の判断待ち、または入力待ち。
StopClaude が応答を終えた — タスク完了。
SubagentStopサブエージェントが作業を終えた。
SessionEndセッションの終了 — 行が「消える」瞬間。

例 1: 待ちになったら macOS 通知を出す

定番の QoL フックです。~/.claude/settings.json に: 

{
  "hooks": {
    "Notification": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"入力を待っています\" with title \"Claude Code\" sound name \"Glass\"'"
          }
        ]
      }
    ]
  }
}

macOS 向けの他のバリエーション（ターミナルベル、iTerm2/Ghostty のネイティブ通知、 Stop でのサウンド再生など）は 「Claude Code の通知を macOS で受け取る」 にまとめています。

例 2: 各セッションの状態をファイルに書き出す

通知は一瞬で消えますが、ステータスファイルならいつでも読めます — シェルプロンプトからも、 tmux のステータスバーからも、自作スクリプトからも。次の構成は ~/.claude/session-status/ にセッションごとの JSON ファイルを保ち、状態が変わるたびに 更新します。 

{
  "hooks": {
    "UserPromptSubmit": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh running" } ] }
    ],
    "Notification": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh waiting" } ] }
    ],
    "Stop": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh done" } ] }
    ],
    "SessionEnd": [
      { "hooks": [ { "type": "command", "command": "~/.claude/track-status.sh ended" } ] }
    ]
  }
}

そして ~/.claude/track-status.sh（chmod +x で実行権限を付与）:

#!/bin/bash
# stdin のフックペイロードを読み、セッションごとのステータスファイルを書く。
STATE="$1"
DIR="$HOME/.claude/session-status"
mkdir -p "$DIR"

PAYLOAD=$(cat)
SESSION_ID=$(echo "$PAYLOAD" | jq -r '.session_id')
CWD=$(echo "$PAYLOAD" | jq -r '.cwd')

if [ "$STATE" = "ended" ]; then
  rm -f "$DIR/$SESSION_ID.json"
else
  jq -n --arg state "$STATE" --arg cwd "$CWD" \
    '{state: $state, cwd: $cwd, updated: now | todate}' \
    > "$DIR/$SESSION_ID.json"
fi

これで cat ~/.claude/session-status/*.json が全セッションのライブ状態を返すように なり、ファイルを読めるものなら何でも — tmux のセグメントでも、メニューバー用スクリプトでも — それを表示できます。

hooks を「本物のモニター」にするために必要なもの

ステータスファイル方式は実際に機能しますし、ライフサイクルを理解するには最良の教材です。 ただし「ディスク上のファイル」を「ひと目で信頼できる何か」にするには、地味な作業が 長く続きます。

  • 待ちの理由の分類 — 許可プロンプト・質問・プランレビューでは緊急度が違います。ペイロードが与えてくれるのは素材であって、分類ではありません。
  • 古い状態の掃除 — Ctrl-C で殺されたセッションや閉じられたターミナルでは SessionEnd が発火しないことがあり、ファイルが残り続けます。
  • 実際に目に入る UI — tmux からファイルをポーリングする方式は、tmux にいない日には機能しません。モニターは「必要な瞬間に視界にある」ことで初めて役に立ちます。
  • 戻る導線 — セッション abc123 が待ちだと分かっても、該当のターミナルタブや IDE ウィンドウを探す作業は残ります。

すでに出来上がったモニターを使う選択肢

AgentManager はこれを最初から最後までやってくれる macOS アプリです。 全 Claude Code セッションが 1 つのフローティングウィンドウに並び、実行中・完了・確認待ちの 状態が、確認待ちの理由付きで表示されます。どれかのセッションが入力を必要とした瞬間に ウィンドウが自動で現れ、全て解消すると引っ込みます。行をクリックすれば該当のターミナルの ペイン・タブや IDE ウィンドウへ直接ジャンプ。メンテすべきスクリプトはありません。
