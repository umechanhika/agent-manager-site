Claude Code の複数セッションを管理する方法

更新日: 2026年8月26日

Claude Code は数分単位で自律的に作業を進めてくれます。だからこそ 2 つ目、3 つ目のセッションを 開いて並列で走らせたくなる — ここまでは自然な流れです。難しいのはセッションを起動することでは なく、全セッションの状況を把握し続けること。どれがまだ実行中で、どれが完了して、 どれが 10 分前から黙って許可待ちになっているのか。この記事では、Claude Code を並列運用するための 実践的なセットアップを紹介します。

そもそも、なぜ複数セッションを走らせるのか

1 セッションだけの運用では、Claude が作業している間こちらが待つだけの時間が生まれます。 並列化する典型的な動機は次の通りです。

  • 独立したタスクの同時進行 — あるリポジトリのバグ修正、別リポジトリのリファクタ、ドキュメント更新など。
  • 長時間タスクの裏で別作業 — マイグレーションや大きなテストスイートを流している間に、別セッションで PR レビューを進める。
  • 調査と実装の分離 — 1 つのセッションで設計の検討をさせつつ、決定済みの実装をもう 1 つで進める。

トレードオフは明確で、セッションを増やすほど「自分がボトルネックになっているのに気づかない」 確率が上がります。Claude Code はコマンド実行やファイル編集の許可、質問への回答、プランの承認が 必要になると停止して待ちます。待ち状態のセッションは音も出さずフォーカスも奪いません — ただ静かに止まっているだけです。

1. セッションごとに作業コピーを分ける（git worktree）

同じチェックアウトで 2 セッションを走らせると、互いのファイル編集が衝突し、 git status もノイズだらけになります。同一リポジトリで並列作業をするなら、 セッションごとに git worktree を切るのが定石です。 

cd ~/code/myapp
git worktree add ../myapp-fix-login fix/login-timeout
git worktree add ../myapp-refactor refactor/db-layer

# ターミナルのタブ 1
cd ../myapp-fix-login && claude

# ターミナルのタブ 2
cd ../myapp-refactor && claude

worktree はブランチごとの完全なチェックアウトですが .git の実体は共有されるため 軽量です。セッション同士が未コミットの変更を踏み合うことは構造的に起きません。 作業が終わったら git worktree remove で片付けられます。

2. どのセッションがどれか、ターミナル上で識別できるようにする

セッションが 3 つを超えると「API リファクタはどのタブだっけ？」が現実の問題になります。 効くのは次のような習慣です。

  • 1 タスク = 1 タブ（または tmux ウィンドウ）にして、タスク名を付ける。多くのターミナルはタブ名を変更でき、tmux なら tmux rename-window api-refactor。
  • 並び順を固定する — 例: いちばん左のタブは常に「メイン」のタスク。
  • Claude Code のステータスラインを設定する — /statusline コマンドでカスタムのステータスライン（モデル名・git ブランチ・コンテキスト使用量など）を設定でき、各セッションが自己説明的になります。~/.claude/settings.json の statusLine 設定で手動構成も可能です。

3. セッションが自分を必要とした瞬間に通知を受け取る

タブに名前を付ければ「どれがどれか」は解決しますが、「どれが今自分を待っているか」は 分かりません。Claude Code にはその瞬間を知らせる仕組みが複数あります。

  • ターミナルのネイティブ通知 — Ghostty・Kitty・iTerm2 では、Claude Code の入力待ちを macOS のデスクトップ通知として受け取れます（iTerm2 は Settings → Profiles → Terminal で通知を有効化）。
  • ターミナルベル — ~/.claude/settings.json に "preferredNotifChannel": "terminal_bell" を設定すると、多くのターミナルがベルの鳴ったタブに印を付けてくれます。
  • hooks — Notification フックイベントは Claude が入力や許可を待ち始めたときに発火し、macOS 通知の送信など任意のコマンドを実行できます。

それぞれの詳しい手順は姉妹記事 「Claude Code の通知を macOS で受け取る」と 「hooks でセッション状態を把握する」で 解説しています。

このセットアップの限界

通知が教えてくれるのは「何かが起きた」という一度きりの事実です。複数セッションを走らせて いると、それは「全体の状況が分かる」こととは別物だと気づきます。

  • macOS のバナーは数秒で消えます。別セッションの作業に集中していたら、それで終わりです。
  • 通知が 2 連続で届いても、どのセッションがまだ待っていて、どれが対応済みなのかは分かりません。
  • 必要なアクションの種類 — 一瞬で済む許可なのか、レビューすべきプランなのか、完了報告なのか — は、タブを切り替えて見るまで分かりません。
  • セッションが増えるほど頭のオーバーヘッドも増え、結局は人間 cron のようにタブを巡回することになります。

スケールするのは、全セッションの状態を常に一覧できる持続的なビューです。IDE がビルドタスクに 対して提供しているようなものを、Claude Code のセッションに対して持つイメージです。

Claude Code セッション専用のモニターという選択肢

AgentManager はまさにこの用途のための macOS アプリです。全 Claude Code セッションを 1 つのフローティングウィンドウに表示し、実行中・完了・確認待ちの状態を、 確認待ちの理由（許可・質問・プランレビュー）付きで一覧できます。ウィンドウは どれかのセッションが入力を必要とした瞬間に自動で現れ、全て解消すると引っ込みます。行を クリックすれば、そのセッションのあるターミナルのペイン・タブや IDE のウィンドウへ直接 ジャンプします。
